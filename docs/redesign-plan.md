# 大改候选方案：PTP 两步报文关联与选主判定核验

日期：2026-10-19（Asia/Shanghai）。当前版本：0.3.0。状态：新增观察上下文、pending/deadline 生命周期、BMCA 有效快照和逐项 evidence 报告已实现；本轮本地 check、测试、CLI、info/fmt 均已通过，详细日志见 [验收记录](validation.md)。完整授权 IEEE 正文未取得，规范门禁不得标为全通过。原计划实施时只完成本地项目。2026-10-22 用户已新授权向指定 GitHub/GitLink 按内容分批同步并发布 Mooncakes；当前外部状态以 `research/publication/current.json` 为准，正式报名由本人办理。逐项映射见 [计划要求核对表](plan-requirements-audit.md)。

## 1. 先明确可以承诺的范围

用户要求任何类似或重合均不可接受。若该条件包括时间表示、字节解析、状态关联、规则校验和报告等基础能力，则任何软件方案都无法被本次生态检索证明为绝对零相似。本方案不会把“未命中关键词”写成“已证明零重合”，也不会把功能领域不同写成自动符合赛事规则。

本方案的可审查目标是：找出与已有项目不同的具体核心输入、规则、输出和用途；移除当前已经确认相近的独立功能；把仍有共同基础能力及未核实部分公开列出。是否允许这些共同基础能力，必须根据完整赛事原创性条款确认。条款尚未确认时，原创性门禁为“未核实”，不能宣称通过。

本轮保存新的全量索引与正文，不复用上一轮正文缓存；另对重点项目的发布 ZIP 进行只读检索。检查覆盖和逐包证据见 [本轮审查记录](../research/2026-10-19-redesign/review.md)。它仍不是全站所有源码、历史版本的穷举证明。

## 2. 推荐方向与淘汰方向

推荐候选：**一个严格限于指定 IEEE 1588 PTP 范围的离线协议核验库，检查 two-step 报文关联和声明的 BMCA 选主结果，并解释违反了哪条具体规则。** 暂用命令名 `ptp-audit`；最终包名、元数据在实现和再次查重后再定。

使用场景：开发者已有 PTP 原始负载、捕获位置及必要时间戳/候选集，想检查报文是否被错误配对、主时钟更换后是否继续使用旧交换、候选比较是否选错，以及证据是否足以计算同步量。工具不调整操作系统时钟。

核心输入：PTP 负载字节；捕获点与时间戳域等观察元数据；明确的检查范围；核验选主时提供具有明确完整性假设的候选数据及待核对决策。

核心输出：逐规则的 `Pass / Violation / InsufficientEvidence / Unsupported`，每项带报文编号、字段位置、使用的数据、期望/实际值、规则依据和假设。`Pass` 只针对已支持且证据充分的规则，绝不代表网络全局符合标准或实际同步精度达标。

不选择以下路线：

| 路线 | 不作为主方向的原因 |
|---|---|
| 通用网络/时钟同步仿真器 | Moonnet、MoonSim、MoonLab、Lockwire、无线信道模拟等已有明显交集 |
| 高精度时间库、PI/PID 控制库 | 现有时间库及通用控制/同步方向难以支持零相似主张 |
| 只扩展消息编解码 | 协议专属性较明确，但单一公共头不足以形成完整交付；通用报文编解码本身已有大量项目 |
| 通用协议一致性、见证、最小反例、模型检查框架 | MCP conformance、EvoWitness、事务见证、CTL 等已有相应工具；报告和反例不是独有创新 |
| 一次完成真实 PTP daemon、硬件时间戳、全部 profile | 验证面过大，硬件和标准兼容风险高，且不能据功能增多消除相似性 |

## 4. 首版范围与不支持范围

当前实现范围：IEEE 1588-2008、限定的 default multicast/E2E/two-step 子集。实现已按该范围落地，但“先取得完整可核实规范依据再冻结范围”的原计划门禁并未因此自动满足；当前公开来源的覆盖和限制见 [逐规则依据表](rule-traceability.md)。不声称覆盖全部标准。

正式支持消息：Sync、Follow_Up、Delay_Req、Delay_Resp、Announce 的指定版本固定字段；公共头和已支持消息体的标准编解码。未知消息、未知 TLV、超出范围的 profile 不得悄悄接受后宣称通过，应返回 `Unsupported` 或按已核实的扩展规则保留原始字段。单步 Sync 的可识别性与实际核验支持分开声明。

首版不实施 NTP/EtherCAT DC、通用日期时间格式化、PCAP/PCAPNG 解析、TCP/UDP 通信、通用离散事件仿真、PI/PID 伺服、系统调钟、硬件采集、通用模型检查和自动最小反例搜索。外部抓包工具可以输出 PTP 负载和元数据；本项目只核验这些明确输入。未来接入现有解析库也不能宣传其解析能力为本项目独有。

## 5. 必须交付的三个协议核心

### A. 标准报文和 correctionField 的严格语义

- 规范字段宽度：48 位秒/32 位纳秒、有符号 64 位 scaled-nanoseconds correctionField（单位为 2^-16 ns），逐字段对应已核实规范。
- 保留亚纳秒分量，不通过 Double 截断，不把原始 correction 整数直接当整纳秒。
- 校验纳秒值域、消息最小长度、消息长度与输入边界、消息类型及版本、sourcePortIdentity 和保留字段的已支持规则。
- 对整数溢出、长度不足和不支持扩展返回明确错误；不另外输出通用整数或时间库。
- 标准字节样本必须来自独立参考或人工按规范构造并经独立工具核对。仅由自己的编码器生成、自己的解码器读回，不能证明符合标准。

### B. two-step 交换的字段关联核验

- 按 profile、domain、消息类型、来源端口身份、sequenceId 及请求身份等已核实规则关联消息，不能只用一个序号作为键。
- 区分到达顺序和协议因果关系：Follow_Up 先于 Sync、重复、缺失、多主时钟交错、序号回绕和主时钟切换均有明确状态。
- Delay_Resp 必须检查所应答请求的身份；不把其他请求方的响应拼进当前交换。
- 关联状态有容量和过期策略，但只有具备正确时间域和超时依据时才判超时；输入结束而未观察到响应通常是证据不足，不能等同于实现违规。
- 只有 t1/t2/t3/t4 来源和时钟域明确、所需 correction 充分且路径假设成立时才输出测量结果。单侧抓包不足、时间戳域不可比较或窗口不完整时输出 `InsufficientEvidence`。
- 仅据普通四时间戳交换不能唯一识别真实路径不对称或证明绝对时钟误差；这些结论不列入产品能力。

### C. 限定范围内的 BMCA 决策核验

- 固定支持的数据集和状态前提，核验质量、身份、路径/拓扑等规范需要的比较项；不是复用目前六字段排序后改名。
- 输出两候选间第一个决定胜负的规则及具体值；多候选选择带逐步依据。
- 同 grandmaster、不同 grandmaster、身份与端口区分、边界质量、空集及相等情形均有独立测试；超出支持范围的情形返回 `Unsupported`。
- 核验“实际选了谁”需要输入设备决策事实；仅看到 Announce 不足以知道设备实际行为。
- 候选集完整性、Announce 有效期和捕获窗口是显式假设；无法确认时不把未观察到的候选当作不存在。

以上三项共同形成一个完整离线核验流程，不把编码器、格式化报告或通用“证据生成”拆成独立创新点。

## 6. 面向使用者的最小闭环

拟定流程：准备案例文件 → 执行 `ptp-audit check case.json` → 得到终端摘要和结构化报告 → 按报文编号与字段定位原因 → 修改输入/被测实现后重检。

首版必须内置以下可复现案例，每例有固定输入、预期判定、规则依据和来源：

| 案例 | 应产生的结果 |
|---|---|
| 范围内、证据完整的 two-step + Announce 案例 | 仅已检查规则通过，输出已使用的假设 |
| 同序号但不同来源/不同 domain 的交错消息 | 互不错误配对 |
| 实现声称用错误来源的 Follow_Up 完成交换 | 定位具体身份/关联矛盾；没有完成声明时只显示无法完成的关联 |
| Follow_Up 先到、重复、序号回绕 | 按确定的关联规则处理，不因简单 `<=` 比较误判 |
| 缺少远端时间戳、采集结束过早 | `InsufficientEvidence`，不得出具全通过 |
| correction 含负值及亚纳秒分量 | 精确保存及运算，独立样本核对 |
| 两候选仅一个决定性字段不同 | 指出规范规定的决定项，核对声明的选主结果 |
| 同 grandmaster 的路径比较和超范围 profile | 支持规则明确判定；超范围返回 `Unsupported` |
| 畸形长度、异常字段、资源上限 | 有界失败，定位字段或资源限制，不崩溃 |

报告必须显示规范版本、规则集版本、输入摘要、覆盖规则、假设、无法检查项和判定定位。相同输入和相同版本产生相同的语义结果；报告格式本身不作为独有能力。

## 7. 架构与迁移顺序

当前包结构：`wire/`（协议字节与受检字段）、`exchange/`（PTP 消息关联和生命周期）、`observation/`（epoch、捕获窗口、时钟域和 deadline policy）、`bmca/`（数据集比较及有效 Announce snapshot）、`audit/`（组合核验结果）、`evidence/`（字段、计算与规则证据）、`diagnostic/`（四态诊断）、`cmd/ptp-audit/`（命令行）。当前输入 schema 为 `ptp-audit/v1`，报告 schema 为 `ptp-audit-report/v2`；内部类型不无故暴露为通用工具库。

阶段按依赖顺序推进，只有前一门禁通过才进入下一阶段：

| 阶段 | 具体产物 | 退出条件 |
|---|---|---|
| 0：冻结范围和相似性审查 | 全量新索引、逐包文档记录、相关源码审查、功能对照、规范来源/条款表、赛事原创性条款核对 | 不存在已确认同核心功能的项目；规范可核实；赛事条件可核实。未核实项保持未通过，不带着假设宣称安全 |
| 1：标准 wire | 受检字段、五类消息固定部分、独立标准字节样本 | 每条支持规则有明确依据；独立样本、边界和负例通过；接口无仿真或系统调钟入口 |
| 2：two-step 核验 | 关联键、资源/窗口策略、时间域与证据状态、错误定位 | 交错、乱序、重复、回绕、缺失等样本全部得到正确且有范围的结果 |
| 3：BMCA 核验 | 明确范围的数据集比较、决策解释、设备声明对照 | 独立参考向量覆盖规范分支；不把未支持的完整 BMCA 情形判作通过 |
| 4：完整交付 | 库、CLI、上述案例、说明、来源/许可证、CI、生成接口与演示 | 全部验收矩阵闭环；`moon test` 及适用目标验证；最后 `moon info && moon fmt` 并审核 `.mbti` 变化；删除旧仿真入口且材料同步 |
| 5：提交前复查 | 新日期全量索引/文档、变更包审查、核心功能再对照、正式提交材料 | 相似性和官方规则仍无未解决项；否则停止提交，不以已有测试通过代替参赛资格 |

## 8. 仍然存在的相似性与转向条件

新方向仍与通用校验器共享“输入、规则、诊断”抽象，与现有时间和报文工具共享时间/字节基础，与协议测试工具共享一致性检查概念。缩小公开 API 和移除通用仿真可以降低具体功能交集，但不能让基础概念消失。

发现同版本/同 profile 的 PTP two-step 关联核验或 BMCA 决策核验已有包时，应重新评估候选，而不是仅增加报告格式或改名。若赛事不允许任何共同基础能力，或无法确认其允许粒度，则本方案不能声称满足用户的字面零类似要求，应保持“不通过/未核实”而非继续包装。

不以改名、换行业措辞、移动文件、隐藏实现、清除历史或只调整 README 解决功能重合问题。标准算法的实现价值也不等于算法本身为作者原创。

## 9. 0.3.0 本地增强：把协议差异落实到验收用途

这一节记录 2026-10-20 在原有 five-message／four-frame／BMCA 核心上的增量实现。版本保持 0.3.0；该段为新增能力形成时的本地记录，发布状态见当前发布凭据。前文原始验收数字是各自时间点的记录；当前代码和运行结果见 [验收记录](validation.md)，不能用历史基线代替新增能力验证。

改进的对象是三个具体使用问题：为什么某次 PTP offset 与被测实现不一致、应用给定的精度上限是否有足够证据作判断、选主改变后提交的交换是否仍来自旧 master。它们围绕原始 PTP 字段和明确决策证据实施，不把通用时间线、窗口、区间、结构化报告或误差传播作为新增独有功能。

| 原差异核心 | 已增加的实际能力 | 对应实现与可复现材料 |

误差预算需要调用者提供四个时间戳绝对误差上界、三个参与 correction 的聚合误差上界、全路径不对称绝对上界、应用 offset 上限、来源、假设及相对速率误差已纳入的确认。区间是保守绝对界传播，不是统计置信度，也不从交换中识别真实路径不对称。预算来源真实性仍须外部负责。
